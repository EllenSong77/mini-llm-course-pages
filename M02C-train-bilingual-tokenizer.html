1. 先分清 v0 和最终版

这节的 Tokenizer v0

用一份小而有代表性的中英双语语料跑通训练、保存、加载、编码、解码和质量对比。它会供 M3 数据管线开发使用。

300M 的正式 Tokenizer

等 M3 整理好真实预训练语料后，用相同流程重训；通过更大测试集后冻结版本，训练模型期间不再随意更换。

这节不再重复手写生产级 BPE。你的责任是理解输入输出、关键配置和质量报告，并能识别 tokenizer 明显切坏的样本。

2. 准备一份小而多样的训练语料

创建 data/tokenizer_demo.txt，每行一条独立文本。建议 500–2000 行，内容必须有权使用。演示阶段可以用你自己写的或 AI 生成并人工抽检的句子。

类别至少覆盖原因
中文日常表达、技术说明、不同标点观察常见词组与单字的切分。
英文普通句子、长单词、缩写观察词根、词缀和空格边界。
中英混合PyTorch、GPU、300M 等贴近未来技术语料。
代码与数字函数、变量、版本号、日期、小数检查符号和数字是否被切得过碎。
少见字符emoji、全角符号等观察未知 token 和字符覆盖。

训练前做两个检查：文件必须是 UTF-8；随机查看至少 30 行，确认不是同一句话机械重复，也没有乱码或隐私内容。

重复同一句 1000 次只会放大它的频率，不会创造语言多样性。Tokenizer 需要看到不同的字符组合和边界。

3. 用 SentencePiece 训练两个候选

在服务器课程环境中安装：

python -m pip install sentencepiece

新建 m2/train_sentencepiece.py：

from pathlib import Path
import sentencepiece as spm

DATA_FILE = "data/tokenizer_demo.txt"
OUTPUT_DIR = Path("artifacts/tokenizers")
OUTPUT_DIR.mkdir(parents=True, exist_ok=True)


def train(vocab_size):
    prefix = OUTPUT_DIR / f"bilingual_bpe_{vocab_size}"
    spm.SentencePieceTrainer.train(
        input=DATA_FILE,
        model_prefix=str(prefix),
        model_type="bpe",
        vocab_size=vocab_size,
        character_coverage=0.9995,
        unk_id=0,
        bos_id=1,
        eos_id=2,
        pad_id=3,
        hard_vocab_limit=False,
        shuffle_input_sentence=False,
    )
    return prefix.with_suffix(".model")


for size in (256, 512):
    print(train(size))

运行后，每个候选会生成：

  • .model：编码/解码真正要加载的模型。
  • .vocab：方便人类查看 token 词表。

关键参数只理解这些

参数人话解释
model_type="bpe"使用上一节学过的高频相邻片段合并思路。
vocab_size希望词表达到的容量；小语料可能凑不满，所以演示时关闭硬性限制。
character_coverage希望直接覆盖训练语料中多大比例的字符；极少见字符可能落入 UNK。
unk/bos/eos/pad_id显式固定特殊 token 的 ID，避免后续模型和数据管线各自猜测。
shuffle_input_sentence=False演示阶段保持训练输入顺序稳定，便于复现实验。
hard_vocab_limit=False 只是照顾小型演示语料。务必打印 sp.get_piece_size()，确认两个候选实际生成了多少 token；不要只相信文件名里的 256/512。

4. 固定测试集，查看它到底怎么切

新建 m2/evaluate_tokenizer.py，测试文本不能拿去训练 tokenizer：

TEST_SAMPLES = [
    "我正在从零训练一个三亿参数的语言模型。",
    "Large language models predict the next token.",
    "PyTorch支持BF16和多GPU训练。",
    "loss = cross_entropy(logits, targets)",
    "版本v2.1发布于2026-09-04，准确率为98.7%。",
    "一个训练语料里没有出现过的长单词: tokenization",
    "你好👋，今天的GPU利用率怎么样？",
]

对两个模型分别打印：

import sentencepiece as spm


def inspect(model_file):
    sp = spm.SentencePieceProcessor(model_file=model_file)
    total_tokens = 0
    total_chars = 0
    total_unk = 0

    print("actual vocab size:", sp.get_piece_size())
    print("special ids:", sp.unk_id(), sp.bos_id(), sp.eos_id(), sp.pad_id())

    for text in TEST_SAMPLES:
        pieces = sp.encode(text, out_type=str)
        ids = sp.encode(text, out_type=int)
        decoded = sp.decode(ids)

        total_tokens += len(ids)
        total_chars += len(text)
        total_unk += sum(token_id == sp.unk_id() for token_id in ids)

        print("\ntext   :", text)
        print("pieces :", pieces)
        print("ids    :", ids)
        print("decoded:", decoded)

    print("\ntokens per character:", total_tokens / total_chars)
    print("UNK count:", total_unk)

tokens per character 是这组测试上“每个字符平均被切成多少 token”。在同一测试集上越低，通常表示序列越短；但它不是唯一质量指标。

人工审查四件事

  1. 能否还原：普通测试句 encode 后再 decode，内容是否符合预期？注意 SentencePiece 可能按其规范化规则处理空格，不要把所有字符串都机械要求逐字节相同。
  2. 有没有 UNK：尤其看 emoji、罕见符号和未见字符。UNK 意味着原始内容的一部分丢失。
  3. 是否切得离谱：常见中英文片段、数字、技术词和代码是否被过度拆碎。
  4. 实际长度：较大词表有没有在固定测试集上真正减少 token 数。

5. 不凭感觉选词表，写一张对比表

候选实际词表大小测试总 tokenUNK 数人工发现的问题

请求 512运行后填写填写填写填写

然后选一个作为 v0，并给出两三句话的理由。不是默认选更大的：如果小语料导致两个候选实际大小接近，或者 512 几乎没有减少序列长度，这本身就是重要结论。

把选中的文件复制或明确记录为：

artifacts/tokenizers/bilingual_v0.model
artifacts/tokenizers/bilingual_v0.vocab
不要删除原候选及配置。Tokenizer 一旦改变，同一段文本的 ID 就可能全部变化；后续数据和模型 checkpoint 必须知道自己对应哪个 tokenizer 版本。

6. 一个故障实验

找一个训练语料和测试集都没有的罕见字符，例如另一个 emoji 或生僻符号，观察它是否变成 <unk>。然后回答：

如果多个不同的原始字符都编码为同一个 UNK ID，decode 时为什么不可能知道原来是哪一个？

只需观察和解释；本节不要求你立刻实现 byte fallback。正式 tokenizer 会在 M3 后用真实字符分布重新决定覆盖与 fallback 策略。
